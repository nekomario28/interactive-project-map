# GitHub Project Galaxy

Turn a GitHub user's public repositories into a living project galaxy with:

- a static SVG for GitHub profile READMEs
- static graph JSON owned by each user
- a shared interactive map with pan, zoom, drag, and repository links
- a hosted preview/install generator
- optional full self-hosting with GitHub Pages

## Recommended architecture: preview centrally, publish from each profile repo

The hosted service is the easiest place to try and configure a map, but permanent README images should be generated by each user's own GitHub Actions workflow.

```text
Hosted generator
    ↓ preview + copy workflow
USER/USER profile repository
    ↓ scheduled GitHub Action
project-map/galaxy.svg
project-map/graph.json
    ↓
GitHub profile README ──click──> shared interactive viewer
                                  ↓
                         static graph.json first
                                  ↓ missing/invalid
                         hosted GitHub API fallback
```

This keeps ordinary profile views off the shared GitHub REST quota. The hosted Worker remains useful for instant previews, installation, and fallback.

## Install in a GitHub profile repository

Open the hosted generator, enter a username, choose the map options, and copy the generated workflow into:

```text
.github/workflows/project-map.yml
```

The workflow uses this repository as a Node 24 JavaScript Action and generates:

```text
project-map/galaxy.svg
project-map/graph.json
```

It runs on a schedule and can also be started manually. Generated files are committed only when their contents change.

The README embed points at the static SVG in `USERNAME/USERNAME` and wraps the image in a link to the user's interactive map:

```html
<p align="center">
  <a href="https://YOUR_DOMAIN/u/USERNAME">
    <img
      width="740"
      src="https://raw.githubusercontent.com/USERNAME/USERNAME/HEAD/project-map/galaxy.svg"
      alt="USERNAME project galaxy"
    >
  </a>
</p>
```

Clicking the image opens the shared viewer. The viewer asks the Worker for a static-first graph. If a valid `USERNAME/USERNAME/HEAD/project-map/graph.json` exists, the Worker validates and renders it without fetching repository metadata from the GitHub REST API. If it is missing or invalid, the normal hosted API is used as a fallback.

### Action inputs

The root `action.yml` supports:

| Input | Default | Meaning |
|---|---:|---|
| `github_token` | required | token used to read public repository metadata |
| `username` | caller owner | GitHub user to visualize |
| `theme` | `dark` | `dark` or `light` |
| `max_repos` | `100` | `1`–`300` eligible repositories |
| `forks` | `true` | include forks |
| `archived` | `false` | include archived repositories |
| `width` | `740` | SVG width, `420`–`1600` |
| `height` | `420` | SVG height, `260`–`1000` |
| `output_dir` | `project-map` | relative generated-output directory |

### Permission isolation

The generated workflow deliberately separates generation from publishing.

```text
generate job
  contents: read
  custom interactive-project-map Action
       ↓ artifact
publish job
  actions: read
  contents: write
  pinned GitHub-maintained Actions + git commit/push only
```

The reusable custom Action therefore does not run in the job that has `contents:write`.

GitHub-maintained Actions in the generated workflow are pinned to full commit SHAs. The generated workflow references this project as `nekomario28/interactive-project-map@v1` for convenience and includes a comment recommending a reviewed full commit SHA when consumers require immutable third-party Action pinning.

**Maintainer release requirement:** after merging the distributed Action, publish a `v1` tag/release before advertising the generated installation workflow. Until `v1` exists, consumers can test with an explicit reviewed commit SHA.

## Hosted preview and fallback

Public endpoints remain available:

```text
GET /api/galaxy.svg?username=USERNAME
GET /api/graph?username=USERNAME
GET /u/USERNAME
GET /api/install-workflow?username=USERNAME
```

Normal `/api/graph` and `/api/galaxy.svg` requests retain their dynamic query semantics. Static profile data is only preferred when the interactive viewer explicitly requests `static=1`, and profile-static cache keys are isolated from dynamic API cache keys.

### Hosted safeguards

The Worker:

- keeps its optional `GITHUB_TOKEN` server-side
- caches normalized dynamic graph data for 15 minutes
- coalesces concurrent cache misses inside a Worker isolate
- uses per-client and upstream Cloudflare Rate Limiting bindings
- validates static graph owner and repository URLs before rendering
- rebuilds groups and edges instead of trusting arbitrary structure from a static JSON file
- limits static graph response size and repository count
- exposes `X-Project-Map-Cache` and `X-Project-Map-Source` for debugging

For installed users, the interactive viewer can return `X-Project-Map-Source: STATIC`; otherwise the fallback is `GITHUB`.

### Deploy the hosted service

Use Node.js 22.18 or newer. GitHub workflows use Node.js 24.

```bash
npm install
npm run verify
npx wrangler login
npm run deploy
```

For production fallback traffic, configure a GitHub token as a Worker secret:

```bash
npx wrangler secret put GITHUB_TOKEN
```

## Optional: self-host with GitHub Actions + GitHub Pages

GitHub Pages remains available for users who want a complete static copy of the application. It is opt-in so forks and hosted-only deployments do not get failing Pages workflows when Pages is disabled.

Configure `config/project-map.json`, then:

1. **Settings → Pages → Build and deployment → Source → GitHub Actions**
2. **Settings → Secrets and variables → Actions → Variables**
3. Create `ENABLE_GITHUB_PAGES=true`
4. Run **Actions → Build and deploy project galaxy → Run workflow**

Without `ENABLE_GITHUB_PAGES=true`, the Pages build is intentionally skipped.

## Query parameters

`GET /api/graph` supports:

| Parameter | Default | Range / values |
|---|---:|---|
| `username` | required | valid public GitHub username |
| `max_repos` | `100` | `1`–`300` |
| `forks` | `true` | boolean |
| `archived` | `false` | boolean |
| `static` | `false` | when true, prefer validated profile static graph before GitHub API fallback |

`GET /api/galaxy.svg` supports the same graph parameters plus:

| Parameter | Default | Range / values |
|---|---:|---|
| `theme` | `dark` | `dark`, `light` |
| `width` | `740` | `420`–`1600` |
| `height` | `420` | `260`–`1000` |

## Repository grouping

Repositories are grouped deterministically from repository names, descriptions, topics, and primary language. Built-in semantic groups include Robotics / ROS 2, AI / Machine Learning, Minecraft Modding, Hardware / Embedded, Web / Apps, and Coursework / Learning. Other repositories fall back to primary-language groups.

## Verification

```bash
npm run verify
```

Verification includes:

- TypeScript type checking
- Wrangler Worker dry-run and binding/config validation
- Node 24 Action entrypoint syntax checking
- Pages script syntax checking
- regression tests for grouping, query parameters, pagination, static Action generation, install workflow permissions, static graph validation, and viewer integration

The repository CI also invokes the local `action.yml` with `contents:read` and checks that a real SVG and graph JSON are generated.
